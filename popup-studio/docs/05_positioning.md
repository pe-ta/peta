# プロダクトの目的（ポジショニング）検討メモ v0.1

- 作成日: 2026-10-14
- 課題: MVP を触ると「バナーを作るツール」に見え、ZEALS にとっての目的が伝わらない。
- 本メモ: 競合・海外プロダクトを「何を約束しているか」で分類し、目的の候補 4 案と推奨を示す。

---

## 1. 参照プロダクトを「約束」で分類する

| 分類 | 代表例 | 一文の約束 | ZEALS への示唆 |
| --- | --- | --- | --- |
| **A. 勝ちクリエイティブを見つける実験エンジン** | CyberAgent 極予測AI（2020〜）、Alia（Shopify ポップアップ）、Atria | 極予測AI: 新案を現行トップと競わせ、勝つと予測した案だけ配信。制作費は成果が出た時のみ（成果報酬）。Alia: クリエイティブ・オファー・配信条件の A/B を AI が継続実行し、売上・LTV で判定 | ZEALS と同じ成果報酬モデルで成立している国内の先行例が極予測AI。「作る」ではなく「勝つ案を見つけ続ける」が約束 |
| B. 制作の内製化・量産ツール | Canva、AdCreative.ai、Creatopy、Rocketium | ブリーフから大量の案をブランド準拠で作る | 汎用ツールと同じ土俵。ZEALS 固有の価値が出ない |
| C. 効果予測で制作を導く | Septeni Odd-AI、CyberAgent 極予測TD/LP、Pencil | 配信前に効果を予測し、人が再設計する（Odd-AI: CTR 約1.1〜1.15 倍、配信量約1.5 倍） | 予測は自社実績データがあって初めて当たる。Phase 3 の要素 |
| D. 成果分析・勝ちパターン資産化 | Motion、Foreplay、Atria | 既存配信のどの要素（フック・訴求・構図）が効いたかを可視化 | 「何が効いたか」を説明できることがクライアント提案力になる |
| E. 承認・校正の高速化 | Ziflow、Filestage | 1 URL 上で注釈と承認を完結し往復を減らす | 単体では地味だが、ZEALS の最大ボトルネック |
| F. 直接競合（離脱防止 → LINE） | Penglue | 離脱タイミングを AI 予測しポップアップ → LINE → ボット。成果報酬 | クリエイティブの実験ループを訴求している競合はいない |

観察:
- 海外では「creative velocity（作って・試して・学ぶ速度）」が収益性と最も相関する、という言説が 2026 年の主流（Segwise、attn 等）。自動化プラットフォームは四半期 30〜40 案を検証、手作業は 8〜10 案という数字もある。
- 極予測AI は ZEALS と同じ「成果が出たときだけ課金」で、**新案が現行チャンピオンに勝つかどうか**を製品の中心に置いている。これが最も近い設計思想。
- 直接競合 Penglue は配信基盤の訴求（タイミング予測・成果報酬）に留まり、クリエイティブ側の約束がない。ここが空いている。

## 2. 目的の候補

| 案 | 一文の目的 | 製品の中心 | 強み | 弱み |
| --- | --- | --- | --- | --- |
| **① 勝ちポップアップ発見エンジン**（推奨） | 離脱ユーザーを LINE に連れてくる「勝ちポップアップ」を、どのクライアントでも 2 週間以内に見つけ、更新し続ける | 仮説 → 変種 → 同時配信 → 勝敗判定 → 次の仮説。チャンピオン/チャレンジャー構造 | 成果報酬モデルと直結（勝率 × 検証数 = 売上）。極予測AI が同モデルで成立実績。Penglue に無い | 成果データ連携（Phase 2）が無いと約束を果たせない |
| ② AP 自走の制作ツール | デザイナーに頼まず AP が当日中にポップアップ案を出せる | ブリーフ → 生成 → 編集 → 書き出し | 今の MVP そのもの。すぐ効く | Canva と区別がつかない。デザイン品質の責任が曖昧 |
| ③ クライアント承認ポータル | 提出 → 承認を 3 日以内に終える | 実機プレビュー・注釈・一括承認・差戻し理由 | 最大ボトルネックに直撃 | 単体では「校正ツール」に見える |
| ④ 勝ちパターン資産化 | ZEALS 全クライアントの「何が効いたか」を説明できる知見にする | DNA タグ × 成果の集計、推奨 | 提案力・採用率に効く。競合が真似しにくい | データが貯まるまで価値が出ない（半年〜） |

## 3. 推奨: ①を目的に据え、②③④を「①を回すための機能」と位置づける

一文: **「ZEALS のポップアップを、"作って提出する成果物"から"勝つまで回す実験"に変える」**

- 製品名の候補: Popup Lab / Challenger / 勝ち筋ラボ（「Studio」は制作ツールに聞こえるため見直し）
- 価値の式: 検証速度 3x × 勝率向上 = LINE 友だち追加数の増加 = 成果報酬の母数拡大
- ユーザーへの約束の順番:
  1. 今週の仮説が 1 日で配信可能な状態になる（②）
  2. クライアント承認が 3 日で終わる（③）
  3. 2 週間でどの案が勝ったか分かり、次の仮説が提示される（①の核、Phase 2）
  4. 半年後、業種別の勝ちパターンで初回提案から当たる（④、Phase 3）

## 4. 目的を①にした場合、MVP の見え方をどう変えるか

| 今の画面 | 変更 | 狙い |
| --- | --- | --- |
| トップ = ブリーフ一覧 | トップ = **実験ボード**。クライアントごとに「現行チャンピオン」「挑戦中の案」「結論の出た仮説数 / 週」を表示 | 開いた瞬間に「実験を回す道具」だと分かる |
| 「生成された案（12）」 | 「チャレンジャー候補（12）」。各案に **検証仮説**を先頭表示、スコアは「配信可否」の意味に | 案の単位が「仮説」であることを明示 |
| 提出 → 承認 | 承認後に **実験に投入**（配信中 / 比率 / 開始日）のステータスを持つ | 承認がゴールではなく配信がゴール |
| 無し | **結果入力**（Phase 2 前は手入力 CSV でも可）と勝敗判定の表示 | 1 周目から「学び」が残る |
| 無し | **学びログ**: 仮説 → 結果 → 次の仮説 の時系列 | 資産化の種 |

これらは要件定義の FR-EXP / FR-LIB を前倒しで「見た目だけ」先に入れる変更で、実装量は小さい。

## 5. 決めてほしいこと

1. 目的を①（実験エンジン）にしてよいか。②（制作ツール）に留めるなら、ロードマップの Phase 2 以降は不要になる。
2. 「勝ち」の定義: クリック率か、LINE 友だち追加率か、CV 率か。成果報酬の計算根拠と揃えるのが筋。
3. 成果データをクリエイティブ単位で取れるか（要件定義 Q4）。取れないなら①は約束できないので、取れる形への配信基盤側の変更が前提条件になる。

## 3. プロダクトの考え方

**一文**: ZEALS のポップアップを、「作って提出する成果物」から「勝つまで回す実験」に変える。

- **North Star**: 結論の出た仮説の数（週あたり）。導入前の 3 倍が目標。
- **価値の式**: 検証速度 3 倍 × 勝率の向上 = LINE 友だち追加数の増加 = 成果報酬の母数の拡大。
- **実験の単位は「仮説」**。案（クリエイティブ）は仮説の具体化。
- **辛口分析の役割**は 2 つに限定する。配信前の足切りと、チャンピオンとの差分の言語化。勝敗の予測は実績が貯まるまで判定に使わない。
- **ボトルネックは制作ではなく待ち時間**（推定: 全体の 6〜7 割がクライアント返答待ちなど）。制作・承認・計測の 3 工程を同時に短くする。
- **参考にした先行例**: CyberAgent 極予測AI（成果報酬・チャンピオン方式）、Alia（ポップアップの AI 自動テスト）、直接競合 Penglue（離脱防止 → LINE、クリエイティブ実験の訴求なし）。詳細は `05_positioning.md`。

## 4. 過去ポップアップから分かった事実（実データ）

対象は共有ドライブの 1,195 件。取り込めたのは 1,069 件。詳細は `07_popup_inventory.md`。

| 項目 | 事実 |
|---|---|
| サイズ | **900×1265 px の縦型が 90%**。事実上の納品標準 |
| 形式 | PNG 770、GIF 251（約 24%）、その他少数 |
| GIF の動き | 2 フレームの点滅が GIF の 43%。ほかに指カーソル、キラキラ等の装飾。ループ中央値 2.25 秒、全件無限ループ |
| 構造 | 帯 → 質問見出し → ビジュアル → 小バッジ → ボタン対 の 5 段構造 |
| ボタン | 2 ボタン（否定＋肯定）59%、CTA 1 本 26%、多択 7%。最多は「いいえ／はい」（503 件） |
| フック | 7 系統: 相性診断（最多 526）、二択タイプ診断、キャンペーン特典、悩み共感、価格知りたい、招待状、クイズ |
| 制作慣行 | 命名規則 `クライアント_案件番号7桁_popup_バリエーション`。**1 案件あたり 1〜2 枚が 7 割**で、比較検証の数自体が少ない |
| 設計意図の痕跡 | ファイル名に「アンカリング向け」「ゲイン・フレーミング」「損得回避バイアス向け」などの行動経済学タグ |
| 規模 | クライアント 270 社、案件 379 件 |
| 欠けているもの | **配信実績（表示・タップ・友だち追加・CV）が無い**。どの型が勝ちやすいかはまだ言えない |

追加で、共有ドライブの 4 フォルダを一覧化したところ **13,333 件**のファイルがあると分かりました（取り込み済みは約 1,200 件のみ）。一覧は作業領域に保存済みで、取り込むかどうかは未決定です。

## 5. 機能仕様（実装、移植時に再現する対象）

### 5.1 実験の流れ

```
ブリーフ作成 → 仮説（フック）ごとに案を生成 → 辛口分析とプリフライトで足切り
→ クライアント承認ポータル → 書き出し・入稿 → 配信開始
→ 結果の取り込み（日次） → 勝敗判定 → 昇格 or 終了 → 学びログ → 次の仮説
```

### 5.2 画面

| 画面 | 内容 |
|---|---|
| 実験ボード | クライアントごとの段階（案作成中 / 確認待ち / 配信待ち / 検証中 / 結論を出す / 次の仮説が必要）、滞留日数、滞留アラート、次にやること。週次の結論数グラフ、4 週平均、仮説から結論までの日数 |
| ブリーフ | 勝ちの定義、オファー、ターゲット、離脱文脈、ブランド色、LP URL（タイトル・OG 画像・色を自動抽出）、フック × ビジュアル × 動き の選択 |
| ブリーフ詳細 | 次にやること、実験欄（チャンピオン vs 挑戦者、判定、推移グラフ、結果入力）、仮説バックログ（おすすめ付き）、挑戦者候補、過去の類似案、承認ポータルとレポートのリンク、学びログ |
| 案の詳細 | 辛口分析、プリフライト、文言・色・動き・型の編集と再描画 |
| 承認ポータル | ログイン不要の署名付きリンク。実機に近いプレビュー、案ごとの承認／修正依頼（理由タグ＋コメント） |
| クライアント向けレポート | 閲覧専用の別署名リンク。現行案、検証中の案と推移、勝敗と学び、最初の案からの改善率、次の仮説。社内用語なし。印刷で PDF 化 |
| 学びライブラリ | 結論をフック・構造・レイアウト・ビジュアル・動き・業種・説得戦略タグ別に集計した勝率 |
| 型の一覧 | マスターテンプレート 7 型のプレビューと追加手順 |

### 5.3 生成とテンプレート

| 軸 | 選択肢 |
|---|---|
| フック（7） | 相性診断、招待状、悩み共感、キャンペーン特典、クイズ、二択タイプ診断、価格知りたい |
| ビジュアル（2） | ブランド色の装飾、写真（LP の OG 画像など） |
| 動き（4） | 静止（PNG）、点滅（GIF）、指カーソル（GIF）、ポップイン（GIF） |
| 型（7） | 質問・2ボタン、招待状、キャンペーン、多択、全面写真、吹き出し質問、二択タイル |

- 文言のスロット: 帯、質問見出し、補足、小バッジ、肯定ボタン、否定ボタン、選択肢（多択時）。
- **文字は画像生成 AI に描かせず、テンプレートで描画する**（誤字・文字化けを構造的に防ぐ）。
- 生成 AI 未接続時はルールベースの文言で動く。
- 出力は 900×1265 の PNG / GIF。

### 5.4 辛口分析（6 軸）

| 軸 | 見るところ |
|---|---|
| 注目 | 離脱の瞬間に帯と見出しが 0.5 秒で目に入るか |
| 質問の明確さ | 何を聞かれ、答えると何が起きるか 1 秒で分かるか |
| 文脈適合 | 離脱直前の心理に質問が答えているか |
| ボタン対 | 肯定が押しやすく、否定が自然な逃げ道か |
| 信頼 | ブランド・業種に合い、怪しく見えないか |
| 表現の安全 | 景表法・薬機法リスクの低さ |

出力は「総合点 + 一言の総評 + ダメな理由 + 文言レベルの直し方」。チャンピオンがいれば「差分 → 理由 → 判定」の比較推論も出す（参考論文 Creative4U）。70 点以上を提出の目安にしている。

### 5.5 プリフライト

コントラスト比（WCAG）、文字数、最小文字サイズ、クライアント別 NG ワード、要注意表現（効果の断定、No.1 表現、治癒の保証、永続性・安全性の断定、期限・限定表示）、ファイル容量。

### 5.6 判定ロジック（移植時に必ず同じにするもの）

- **勝ちの定義**はブリーフごとに選ぶ: LINE 友だち追加率（既定）、タップ率、CV 率。
- **ベイズ推定**（Beta 分布）で「挑戦者が上回る確率」を出す。95% 以上で勝ち、5% 以下で負けの候補。
- **逐次検定（mSPRT）**で確定したときだけ勝敗を出す。毎日確認しても誤判定が 5% を超えない。シミュレーションでは従来方式 80/300 回の誤判定が 2/300 回に減った。
- **同時期比較**: チャンピオンの、挑戦者の配信開始前の記録を差し引いて比べる。
- 双方 300 表示以上が必要。
- 昇格ボタンはサーバー側でも同じ判定で守る。

### 5.7 仮説の状態（自動算出）

未着手 → 案を作成中 → 検証中 → 結論済み（勝ち／負け／結論なし）。手動で変えられるのは「見送り」と「戻す」だけ。状態は案と学びログから毎回算出する。

### 5.8 次の仮説のおすすめ

このクライアントで未着手のフックを、全クライアントと同業種（重み 2 倍）の勝敗で並べる。検証が少ないフックを 1 つ「探索枠」として入れる。

### 5.9 結果の取り込み

| 方法 | 形式 |
|---|---|
| 貼り付け | CSV / TSV。列は 案ID（`zc=` パラメータ）、日付、表示、タップ、LINE追加、CV、ブロック。日本語・英語の列名どちらも可 |
| API | `POST /api/briefs/<id>/results`、Bearer トークン（ブリーフ画面に表示）。CSV / TSV / JSON の行配列 |

値は日付時点の累計。日次スナップショットとして保存し、推移グラフと逐次検定に使う。

### 5.10 滞留アラートの基準

| 状況 | 基準 |
|---|---|
| 判定が出たのに未処理 | 2 日 |
| 提出後に返事なし | 3 日 |
| 承認後に未配信 | 2 日 |
| 配信後に結果が未入力 | 3 日 |
| 判定が出ない | 3 週間 |
| 下書きのまま | 3 日 |
| 挑戦者がいない | 5 日 |

## 6. 技術構成（実装）

| 項目 | 内容 |
|---|---|
| アプリ | Next.js 16（App Router）、TypeScript、Tailwind CSS v4 |
| 描画 | Satori（JSX → SVG）→ resvg で PNG、gifenc で GIF。フォントは Noto Sans JP を同梱 |
| データ | Postgres（Neon）の JSON 文書テーブル 1 つ。種類は brief / creative / review / learning / hypothesis / snapshot |
| 生成 AI | Gemini / OpenAI / Claude の切り替え層。どのキーが入っているかで自動選択、`LLM_PROVIDER` で固定可能 |
| 配置 | Vercel（東京リージョン） |
| テスト | 単体テスト（判定・取り込み・おすすめ等）、Playwright の E2E 7 本 |

### 環境変数

| 変数 | 用途 |
|---|---|
| DATABASE_URL | Postgres の接続先 |
| GEMINI_API_KEY / OPENAI_API_KEY / ANTHROPIC_API_KEY | 生成 AI。**短尺動画分析ツールと同じ提供元のキーを 1 つ**入れる（依頼者の決定） |
| LLM_PROVIDER、各 *_MODEL | 提供元・モデルの固定（任意） |
| REVIEW_SECRET | 承認リンク・レポートリンク・結果 API の署名鍵。**本番で未設定だとリンクが偽造できる** |
| NEXT_PUBLIC_APP_URL | コピーするリンクの基点 URL |
| NORTH_STAR_BASELINE | 導入前の週あたり結論数（任意） |

## 7. 取り扱いのルール（依頼者談・合意事項）

- API キーやトークンは**チャットに貼らない**。Vercel などの環境設定にだけ入れる。
- `.env` やキーを GitHub に上げない。
- **クライアント名は機密**になりうる。外部に出す資料では必要に応じて仮名にする。過去ポップアップの社名・画像は社外に出さない。
- 過去ポップアップのファイルは共有ドライブ「ZEALS過去クリエイティブ格納フォルダ」にあり、ZEALS アカウントの権限で読む。
- クライアント向けの画面（承認ポータル、レポート）には、社内ナビ・社内用語・設定の警告を出さない。

# Popup Studio 要件定義書 v0.1

- 作成日: 2026-10-14
- 対象: ZEALS 離脱時ポップアップ（PNG / GIF）クリエイティブの制作〜検証ループ
- オーナー: デザイン領域担当（本ドキュメントの依頼者）
- ステータス: ドラフト。§10 の確認事項が解消され次第 v0.2 へ。

---

## 1. 背景

ZEALS のビジネスモデルは、クライアントの Web サイト離脱時にポップアップを表示し、LINE 友だち追加へ誘導、
チャットボットで接客し CV（購入・申込など）に至った時点で成果報酬が発生するもの。加えて LINE PUSH 配信からの CV もある。

ビジネスの最上流にあるのが「離脱時ポップアップ」で、ここのクリック率と LINE 友だち追加率が、
後工程（チャットボット、PUSH）すべての母数を決める。ポップアップの改善速度 = 事業の学習速度である。

### 現状の体制とフロー（ヒアリング内容）

| 役割 | 担当 |
| --- | --- |
| アカウントプランナー（AP） | 営業兼コミュニケーションデザイナー。アカウントを担当し、クリエイティブを依頼・提出・運用する |
| デザインチーム | AP からの依頼でバナー（PUSH 用）・ポップアップ（PNG/GIF）を制作 |
| クライアント | 提出物を確認・修正指示・承認 |

- PUSH 配信用バナー: 依頼から **3 営業日で 6 枚程度**
- ポップアップ: 同様に依頼するが PUSH より時間がかかる。GIF と PNG の 2 形態
- その後クライアント提出 → 修正 → 再提出があり、**1 本の PUSH 配信 / ポップアップが完成するまで 2〜3 週間**

### ミッション

**ポップアップの検証速度を 3 倍にする。** ここで「検証速度」は
「1 クライアントあたり、単位時間に *配信され結果が得られる* ポップアップ仮説の数」と定義する（§5 で指標化）。

## 2. 現状分析（As-Is バリューストリーム）

ヒアリングから推定した 1 本あたりのリードタイム。数値は仮置きで、**実測が最初のタスク**（§10 Q1）。

| # | 工程 | 推定所要 | 待ち or 作業 | 主なムダ |
| --- | --- | --- | --- | --- |
| 1 | AP がブリーフ作成（訴求・ターゲット・参考） | 0.5〜1 日 | 作業 | ブリーフ品質のばらつき → 後工程の手戻り |
| 2 | デザインチームの着手待ち | 1〜2 日 | **待ち** | キュー滞留 |
| 3 | 制作（PNG）/ 制作（GIF はコマ設計分だけ長い） | 1〜3 日 | 作業 | GIF の手作業、サイズ展開の手作業 |
| 4 | 社内レビュー・修正 | 0.5〜1 日 | 作業 | 口頭/チャットでのフィードバック |
| 5 | クライアント提出 → 返答待ち | 3〜7 日 | **待ち** | 最大のボトルネック。確認者が複数、メール往復 |
| 6 | 修正ラウンド（平均 1〜2 回） | 2〜5 日 | 作業+待ち | 修正理由が「好み」「表現規制」「訴求の方向性」に混在 |
| 7 | 入稿・設定 | 0.5〜1 日 | 作業 | 手作業の設定 |
| 8 | 計測して結論が出るまで | トラフィック依存 | 待ち | 1 本ずつ直列で検証、判断基準が不統一 |

- 合計 10〜15 営業日 ≒ ヒアリングの「2〜3 週間」と整合。
- **作業時間は全体の 3〜4 割、残りは待ち時間**（推定）。したがって制作の高速化だけでは 3x に届かない。
  「制作」「承認」「計測」の 3 工程を同時に短縮する必要がある。

### 3x を達成するための配分（目標）

| 工程 | As-Is（推定） | To-Be 目標 | 手段 |
| --- | --- | --- | --- |
| ブリーフ〜初稿 | 3〜6 日 | **同日（〜2 時間）** | 構造化ブリーフ + テンプレート生成 + AI コピー/画像 |
| 社内レビュー | 0.5〜1 日 | 〜2 時間 | 自動プリフライト（規約・可読性・NG）+ 比較ビュー |
| クライアント承認 | 5〜12 日 | **2〜3 日** | 承認ポータル（実機プレビュー・注釈・一括承認）+ 事前合意したガードレール内の「セット承認」 |
| 入稿 | 0.5〜1 日 | 〜30 分 | 仕様準拠の自動書き出し |
| 計測 | 直列 | **並列**（同時 3〜6 案） | 変種を同時配信し、統一された判定ルールで早期終了 |

- 目標リードタイム: **15 営業日 → 5 営業日**。同時検証数も 1 → 3 以上にするため、実効的な検証速度は 3x を超える余地がある。

## 3. プロダクトのゴールと非ゴール

### ゴール（Phase 1〜3 を通じて）

1. AP が **単独で** ブリーフから複数案（PNG/GIF）を生成し、クライアント提出できる状態に到達できる。デザインチームは「量産」から「監修・テンプレート開発・勝ちパターンの設計」へシフトする。
2. クライアント承認を **ポータル上で** 完結させ、往復回数と待ち時間を半減する。
3. ポップアップごとの成果（表示 → クリック → LINE 追加 → ボット起動 → CV）を同一画面で見られ、**勝敗の判定ルールが統一**されている。
4. 勝ちパターンが **学習ライブラリ**に蓄積され、次のブリーフ時に「業種 × オファー × 離脱文脈」で推奨が出る。

### 非ゴール（v1 では扱わない）

- チャットボットのシナリオ設計・LINE PUSH 文面（将来の拡張候補だが、まずポップアップに集中）
- ポップアップの表示ロジック（離脱検知・頻度制御）そのものの置き換え。既存の ZEALS 配信基盤に書き出す前提
- 汎用のバナー制作ツール（Canva 代替）。本ツールは ZEALS の仕様・ファネルに特化する
- LINE 友だち追加後の計測基盤の作り直し。既存の計測データを取り込む

## 4. ユーザーとユースケース

### ペルソナ

| ペルソナ | 目的 | 痛み |
| --- | --- | --- |
| **AP（アカウントプランナー）** | 担当アカウントの CV を伸ばす。クリエイティブを速く回す | 依頼〜納品の待ち。クライアント往復。何が効いたか説明しづらい |
| **デザイナー** | 品質とブランド整合性を守りつつ数を出す | 同じ構図の量産、GIF の手作業、修正理由が曖昧 |
| **クライアント担当者** | 自社ブランド規約・表現規制を守る。成果が出てほしい | 確認依頼がメール添付で来る。スマホでどう見えるか分からない。承認権限者が別にいる |
| **デザイン責任者（依頼者）** | 検証速度を上げ、組織の学習を資産化する | 個人技に依存。知見が散逸 |

### 主要ユースケース（MVP 範囲に ★）

1. ★ AP が新規ブリーフを作成し、仮説グリッド（訴求軸 × ビジュアル軸 × 動き）から生成する案の組み合わせを選ぶ
2. ★ システムがテンプレート + AI コピー + AI 背景画像で PNG/GIF 案を複数生成（数分）
3. ★ プリフライト（ブランド規約・NG 表現・可読性・ファイル仕様）に自動で通し、問題を指摘・自動修正
4. ★ デザイナーが比較ビューで監修し、微調整（テキスト・配置・色）して確定
5. ★ クライアントに承認リンクを送付。クライアントは **自社サイト上に重ねた実機プレビュー**で確認し、注釈・承認
6. ★ 承認済み案を ZEALS 配信仕様で書き出し（PNG/GIF + メタデータ）
7. 配信結果（表示・クリック・LINE 追加・CV）を取り込み、変種間の勝敗を統一ルールで判定
8. 勝ちパターンを学習ライブラリに登録。次回ブリーフ時に推奨として提示
9. 既存の勝ちクリエイティブを「別クライアント向けに翻案」する（構造を保ち、ブランド要素だけ差し替え）

## 5. 成功指標（KPI）

### North Star

**週あたり「結果が出た」ポップアップ仮説数 / クライアント**（配信され、判定ルールで勝敗が確定した数）。
現状値を実測し、**3 倍**を目標とする。

### 先行指標（プロセス）

| 指標 | 定義 | 現状（推定） | 目標 |
| --- | --- | --- | --- |
| リードタイム | ブリーフ作成 → 配信開始 の営業日 | 10〜15 日 | ≤ 5 日 |
| 初稿到達時間 | ブリーフ作成 → 社内レビュー可能な初稿 | 3〜6 日 | ≤ 2 時間 |
| 承認往復回数 | クライアントの修正依頼ラウンド数 | 1〜2 回 | ≤ 0.5 回（一発承認率 ≥ 60%） |
| 承認所要日数 | 提出 → 承認 | 5〜12 日 | ≤ 3 日 |
| 同時検証数 | 1 クライアントで同時配信している変種数 | 1 | ≥ 3 |
| デザイナー工数 / 本 | 制作に要した実働時間 | 要実測 | −70% |

### 結果指標（ビジネス）

- ポップアップ CTR、LINE 友だち追加率（クリック→追加）、追加後のボット起動率、CV 率、**ブロック率**（追加直後のブロックは品質低下の兆候）
- 勝ち案の採用による CVR リフト（ベースライン比）

### 計測の注意点

- 「結果が出た」の定義を統一する（§7.5 判定ルール）。
- ポップアップ単体の CTR 最大化は LINE 追加後の離脱・ブロックを増やしうる。**最終 CV までを評価軸にする**（成果報酬型と整合）。

## 6. スコープ（フェーズ）

| フェーズ | 期間目安 | 含むもの | 検証したいこと |
| --- | --- | --- | --- |
| **Phase 0: 計測** | 2 週間 | As-Is リードタイムと工程別時間の実測。既存 20〜50 本の過去ポップアップと成果データの収集・タグ付け | ボトルネック仮説（承認待ちが最大）の確認。学習ライブラリの種データ |
| **Phase 1: MVP** | 8〜10 週間 | ブリーフ → テンプレート生成（PNG/GIF）→ プリフライト → 比較/監修 → 承認ポータル → 仕様書き出し | 初稿到達 ≤ 2h、一発承認率、AP 単独完結率 |

| **Phase 3: 学習** | 8 週間〜 | 学習ライブラリ、クリエイティブ DNA タグ、推奨エンジン、ペアワイズ比較判定（MLLM）、翻案生成 | 事前スコアと実績の相関、推奨採用時のリフト |

## 7. 機能要件

要件 ID は `FR-<モジュール>-<番号>`。優先度: **Must**（MVP 必須）/ Should / Could。

### 7.1 ブリーフ & 仮説設計（BRF）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-BRF-01 | クライアント・LP URL・オファー（割引/特典/診断など）・ターゲット・離脱文脈（どのページ・どのタイミング）・NG 表現・ブランドキット参照を **構造化フォーム**で入力できる | Must |
| FR-BRF-02 | LP URL を入力すると、LP のスクリーンショット・主要コピー・配色・ロゴ・既存の訴求点を自動抽出し、ブリーフの初期値として提案する | Must |
| FR-BRF-03 | 仮説グリッド: 訴求軸（例: 価格・限定・不安解消・診断・社会的証明）× ビジュアル軸（人物/商品/テキスト主体）× 動き（静止/ループ GIF）× CTA 文言 の組み合わせを提示し、生成する案を選択できる | Must |
| FR-BRF-04 | 各案に「検証したい仮説」を一文で紐づける（後の学習で使う） | Must |
| FR-BRF-05 | 学習ライブラリから、業種・オファー類似の過去勝ちパターンを推奨として表示 | Could（Phase 3） |

### 7.2 生成（GEN）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-GEN-01 | **テンプレートはコード（HTML/CSS）で定義**し、テキスト・画像・色・ロゴをデータとして差し込む。ピクセル生成ではなく、編集可能なレイヤー構造を保つ | Must |
| FR-GEN-02 | 日本語テキストは **HTML レイヤーで描画**（画像生成モデルに文字を描かせない）。フォント・字詰め・禁則を制御し、文字化けや誤字を構造的に排除する | Must |
| FR-GEN-03 | AI コピー生成: 訴求軸ごとにヘッドライン・サブ・CTA の候補を複数生成。文字数上限・NG ワード・景表法/薬機法系の要注意表現を制約として与える | Must |
| FR-GEN-04 | AI 背景/ヒーロー画像生成: 商品・人物・抽象背景をプロンプトから生成、または LP 既存素材をリサイズ/切り抜きして利用。生成画像は商用利用可能なモデルに限定する | Should |
| FR-GEN-05 | GIF 生成: テンプレートの CSS アニメーション（登場・点滅・スライド等のプリセット）をヘッドレスブラウザでフレーム撮影し、GIF に変換。フレーム数・容量を ZEALS 仕様に自動最適化 | Must |
| FR-GEN-06 | 出力は ZEALS ポップアップ仕様（サイズ・容量・形式・セーフエリア）に自動準拠。仕様はテンプレート側に設定として持つ | Must |
| FR-GEN-07 | 1 ブリーフから **3〜12 案を 5 分以内**に生成 | Must |
| FR-GEN-08 | デザイナーが手動で微調整できるエディタ（テキスト編集・要素位置・色・画像差し替え）。Figma 等との往復は任意 | Must |
| FR-GEN-09 | 翻案生成: 既存案の構造を保ち、別クライアントのブランドキットで再生成 | Could |

### 7.3 プリフライト評価（EVAL）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-EVAL-01 | ブランド規約チェック（許容色・ロゴ最小サイズ・余白・フォント） | Must |
| FR-EVAL-02 | 表現チェック: クライアント固有 NG ワード、業界の要注意表現（医療・美容・金融など）を LLM + 辞書で検出し、代替案を提示 | Must |
| FR-EVAL-03 | 可読性チェック: 実機サイズでの最小文字高さ、コントラスト比（WCAG 基準準拠）、CTA のタップ領域 | Must |
| FR-EVAL-04 | 仕様チェック: 容量・寸法・GIF フレーム/秒数・透過の有無 | Must |
| FR-EVAL-05 | 視線/注目ヒートマップ（サリエンシー推定）で、CTA と主訴求に注目が集まるかを可視化 | Should |
| FR-EVAL-06 | MLLM による **ペアワイズ比較判定**（2 案を比較し、どちらがクリックされやすいかと理由を出力）。実績データで校正し、相関が確認できるまでは「参考値」として表示 | Should（Phase 3） |
| FR-EVAL-07 | 評価結果は「スコア + 指摘 + 改善提案」の構造で表示し、一部は自動修正（例: 文字サイズの引き上げ）を提案できる | Must |

### 7.4 レビュー & 承認（APR）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-APR-01 | 社内レビュー: 複数案の並列比較ビュー、バージョン履歴、コメント | Must |
| FR-APR-02 | クライアント承認ポータル: ログイン不要のリンク（期限付き）または招待制アカウント | Must |
| FR-APR-03 | **実機プレビュー**: クライアントの LP スクリーンショット上に実寸で重ねた表示、スマホ/PC 切替、GIF は再生 | Must |
| FR-APR-04 | 注釈（ピン留めコメント）、案単位の承認/差戻し、セット一括承認 | Must |
| FR-APR-05 | 承認ステータスと期限のリマインド（メール/LINE/Slack） | Should |
| FR-APR-06 | 「ガードレール承認」: クライアントとテンプレート・表現ルールを事前合意すると、そのルール内の変種は **簡易承認（通知のみ）**で配信できるフローを設定可能 | Should（契約面の確認が前提: §10 Q6） |
| FR-APR-07 | 差戻し理由をタグ化（ブランド/法務/訴求方向/好み/誤字）し、学習に使う | Must |

### 7.5 配信 & 計測（EXP）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-EXP-01 | 承認済み案を ZEALS 配信基盤の入稿形式で書き出し（ファイル + メタデータ CSV/JSON）。将来は API 連携 | Must |
| FR-EXP-02 | 変種ごとに一意のクリエイティブ ID を発行し、LINE 追加 URL のパラメータ等で後工程と突合できる | Must |
| FR-EXP-03 | 成果データ取り込み（表示・クリック・LINE 追加・ボット起動・CV・ブロック）。CSV 取り込みから始め API 化 | Should（Phase 2） |
| FR-EXP-04 | **統一判定ルール**: ベイズ推定で「A が B を上回る確率」と期待損失を表示し、閾値（例: 95% / 期待損失 < 0.1pt）で早期終了を推奨。少トラフィックのクライアントには最小観測数とタイムボックスを併用 | Should（Phase 2） |
| FR-EXP-05 | 変種への配信比率を自動調整（Thompson Sampling 等）。配信基盤が比率制御に対応する場合のみ | Could |
| FR-EXP-06 | 結果レポート自動生成（クライアント向け: 何を試し何が勝ったか、次の仮説） | Should |

### 7.6 学習ライブラリ（LIB）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-LIB-01 | 全クリエイティブを「クリエイティブ DNA」（訴求軸・オファー種別・レイアウト型・色調・人物有無・動き・CTA 型・業種）で自動タグ付け | Should |
| FR-LIB-02 | 成果と結合し、業種 × 訴求軸などの切り口で勝率・平均リフトを集計 | Should |
| FR-LIB-03 | 類似ブリーフ検索と推奨（Phase 3） | Could |
| FR-LIB-04 | 過去ポップアップ（ツール導入前）の一括インポートとタグ付け | Should（Phase 0 で種データ化） |

## 8. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 性能 | 1 案の PNG 生成 ≤ 10 秒、GIF ≤ 60 秒。12 案並列で 5 分以内 |
| 可用性 | 社内ツールとして 99.5%。承認ポータルはクライアントが触るため停止時のフォールバック（静的 PDF 書き出し） |
| セキュリティ | クライアント別のデータ分離、承認リンクは期限付き署名 URL、生成 AI へ送るデータから個人情報を除外。生成画像の学習利用オプトアウト設定を持つモデル/契約のみ使用 |
| 権利 | 画像生成モデルは商用利用と権利補償の明確なもの（Adobe Firefly / Google / OpenAI の利用規約を確認）。フォントは商用ライセンス確認済みのみ |
| 監査 | 誰が・いつ・どの案を承認したかの履歴。クライアント承認の証跡を保存 |
| 拡張性 | テンプレートは設定ファイル + HTML/CSS で追加できる。評価器はプラグイン構造 |
| 国際化 | 日本語優先。将来の海外展開（ZEALS 米国法人）を妨げない文字列管理 |
| コスト | 1 案あたり生成 API コスト ≤ 30 円を目安（LLM + 画像生成）。月次でモニタリング |

## 9. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| クライアントが承認ポータルを使わない | 最大ボトルネックが解消しない | 既存のメール運用と並走（ポータルリンク + PDF 添付）、AP が同席して初回利用を支援。ポータル利用率を KPI 化 |
| 生成品質がデザイナー基準に届かない | 監修工数が減らない | テンプレートはデザイナーが設計。生成は「素案」位置づけで開始し、採用率を計測して改善 |
| 事前スコアが実績と相関しない | 誤った案を推奨 | Phase 3 まで「参考値」。相関（Kendall τ 等）を継続測定し、閾値未満なら表示しない |
| 画像生成の権利・表現リスク | クライアント信頼の毀損 | 商用利用可モデルに限定、人物は実写素材 or 許諾済み、医療・美容系は表現チェックを強化 |
| ZEALS 配信基盤の仕様が未確認 | 書き出しが使えない | Phase 0 で仕様確認（§10）。仕様はテンプレート設定として外部化 |
| 少トラフィックで検証が終わらない | 同時検証が機能しない | タイムボックス + 最小観測数、クライアント横断の学習で事前分布を強化 |

# 10. 方針転換 v0.5: 実験運用基盤（2026-10-15）

## 決めたこと

- 製品の幹を「AI がポップアップを描く」から「**検証を回す運用の基盤**」に移す。North Star は変わらず「結論の出た仮説の数（週あたり）」。
- 描画はデザインチームのマスターテンプレート（コード）に文言を流し込む方式に固定し、AI 生成画像で美観を競わない。
- 辛口分析は「配信前の足切り」と「チャンピオンとの差分の言語化」に役割を限定する。勝ち予測は実績データが貯まるまで判定に使わない。

## 根拠（1,066 枚の棚卸しから）

- 90% が同じサイズ、6 割が同じ構造（いいえ／はい）、フックの半数が相性診断。描く対象は型に流し込める。
- 1 案件あたり 1〜2 枚が 7 割。比較する仮説がほぼ無く、「作るのが遅い」以前に「検証の数が少ない」。
- ファイル名に意図は残るが、勝敗は資産として残っていない。学習が蓄積しない。

## v0.5 で入れたもの

| 機能 | 画面 | 内容 |
|---|---|---|
| 仮説バックログ | `/briefs/[id]` | 実験の単位を「仮説」にする。優先度・フック・出典・記入者を持ち、「この仮説で案を作る」で下書きを生成。配信で「検証中」、結論で「結論済み（勝ち／負け）」に自動遷移し、学びログと結び付く |
| 配信結果の CSV 取り込み | `/briefs/[id]` | 配信基盤の書き出しを貼り付けて日次スナップショットとして保存。案 ID（`zc=` パラメータ）で突き合わせ、最新行を結果にする。手入力も同じスナップショットに残る |
| 判定までの見込み | 実験テーブル | 配信日数、記録回数、「今のペースならあと約 N 日」（二標本比率の必要表示数 ÷ 直近の 1 日表示数） |
| 実験ボードの段階管理 | `/` | クライアントごとに段階（案作成中 / 確認待ち / 配信待ち / 検証中 / 結論を出す / 次の仮説が必要）、滞留日数、滞留アラート（確認待ち 3 日、承認後未配信 2 日、判定後 2 日、挑戦者不在 5 日 等）、次にやること。やることが多い順に並ぶ |
| 学びライブラリ | `/learnings` | 全クライアントの結論を DNA タグ（フック・構造・レイアウト・ビジュアル・動き・業種・説得戦略）で集計し勝率を出す。n が小さい行は参考表示 |
| マスターテンプレート一覧 | `/templates` | 4 型のプレビューと対応フック、型の追加手順（デザインチーム向け） |

## 次の段階

1. 配信基盤からの結果取得を CSV 貼り付けから自動連携（API か定期取り込み）へ。
2. デザインチームとマスターテンプレートを 10〜20 種に拡張。写真素材の置き場（Blob ストレージ）を用意する。
3. 実績が貯まったら、学びライブラリの勝率を仮説の優先度の初期値に反映し、辛口分析の勝敗予測を較正する。
4. 逐次検定（anytime-valid）への置き換えで、途中で見ても有効な判定にする。
